# zcode（及外部 agent）接入协议

> 适用：非 dsh 的 AI 编程工具（zcode / Cursor / Cline 等）参与本机项目协作时，必须遵守本协议。
> 版本：v3（2026-09-11，**项目号段编号版**——zcode 前缀改为 `Z<项目字母>##`，防多项目并行撞号；上一版 v2 2026-08-28 多 agent 前缀分配表，替代 external-agent-protocol.md 的单一 E## 版）
> 项目根：`{体系根}\<项目名>\`（dsh 主工作区）；外部 agent 各自有独立 worktree（见下）。
> 本协议与 dsh 的三级会话 + 使命登记（`tools\mission.mjs`）体系并存：外部 agent 不使用 project_map/mission.mjs，靠 **git 分支 + worktree + 文件协议**参与。

---

## 一、角色与编号前缀（多 agent + 多项目防混淆）

> **v3 关键改动（2026-09-11）**：zcode 编号从 `Z##` 升为 **`Z<项目字母>##`（项目号段）**。
> 原因：旧规则"从**项目**当前最大编号 +1"是每项目本地计数，而 `Z##` 前缀按全局共享池设计 → 多项目并行时**跨项目撞号**（项目甲 与 项目乙 各有一个 `Z01`）。
> 新规则给每个项目分配**全局唯一字母**，各项目在自己号段内独立编号，互不相撞；且天然支持"每个项目一套独立 zcode 主/域会话"。

### 1.1 agent 前缀（第一段 = 来源）

| 前缀 | 归属 | 说明 |
|---|---|---|
| `S##` | dsh 域会话 | 走使命登记（`tools\mission.mjs declare`）→ 分支 → complete；各项目独立编号池，**不进本协议** |
| `Z<项目字母>##` | zcode | 本协议主对象，每项目专属号段（见 1.2），使用独立 worktree |
| `C<项目字母>##` | Cursor | 未来接入时启用 |
| `K<项目字母>##` | Cline / 其他 | 未来接入时启用（按需继续分配） |

### 1.2 项目字母分配表（**由体系主会话维护，字母全局唯一**）

| 项目 | 字母 | 下一个编号 | 本项目进度 |
|---|---|---|---|
| 项目甲 | `A` | `ZA02` | Z01 已用（旧制），新号段续号 |
| 项目乙 | `Q` | `ZQ11` | Z01~Z10 已用（旧制），新号段续号 |
| plugins n skills | `P` | `ZP01` | 待立项（目录已建，无登记表；旧制曾派 Z11 未登记） |
| blog | `B` | `ZB01` | 未开工 |
| 项目己 | `L` | `ZL01` | 未开工 |
| 新项目 | 立项时在此表认领字母 | — | — |

- **职责切分**：**项目字母**跨项目共享、必须唯一 → 由**体系主会话**在本表分配登记（新项目立项时来此认领）；**序号**跟项目走 → 由**各项目主会话**本地维护（查本项目 `PROJECT.md` 登记表）。
- **取号规则**：`序号 = 本项目历史最大 zcode 编号 + 1`（无历史则从 `01` 起），跨使命不重用。
  - 例：项目甲 旧制最大 Z01 → 下一个 `ZA02`；项目乙 旧制最大 Z10 → 下一个 `ZQ11`；plugins n skills 无历史 → `ZP01`。
- **旧编号保留不迁移**：项目甲 的 `Z01`、项目乙 的 `Z01~Z10` 照旧留在登记表/分支/commit/达成报告里（改名会破坏 git 历史与报告引用），新前缀从**下一件任务**起生效。

### 1.3 命名

- 使命名：`ZA02-fix-login-bug`；分支名：`feature/ZA02-fix-login-bug`；commit：`feat(ZA02): ...`（英文 message）
- 两个 dsh 项目各自的 zcode 会话**编号互不影响**（字母隔离）；同项目内编号跨使命不重用

## 二、独立 worktree（隔离的关键）

外部 agent 一律在**自己独立的 git worktree 目录**里干活，绝不使用 dsh 主工作区：

```
{体系根}\项目甲          ← dsh 主会话 + dsh 域会话(S##) 共用（唯一写者维护共享文档）
{体系根}\项目甲-zcode    ← zcode 所有会话专用（git worktree，新建一次）
{体系根}\项目甲-cursor   ← 未来 cursor 接入时新建（如需）
```

- worktree = 同一个仓库的第二份工作树：共用同一 `.git`（同一项目历史），但各有各的当前分支和文件版本
- zcode 在它工作树里 `git checkout` **不会**切走 dsh 主工作区的分支（2026-08-27 踩过共享工作区互切分支的坑，worktree 是正规解法）
- worktree 由 dsh 主会话派域会话创建，外部 agent 不需要自己建

## 三、接入前必读（开工前先读这几个文件）

1. `PROJECT.md` — 项目当前状态、最近变更、下一步、已知坑（**只读，不修改**）
2. `KNOWLEDGE.md` — 项目架构决策、接口约定、项目特有坑（**只读，不修改**）
3. `ROLES.md`（若存在）— 本项目特定角色分工与约定（**只读，不修改**）
4. `.dsh\missions\` 目录 — 当前有哪些活跃使命（避免撞同一文件）

---

## 四、铁律（违反 = 改动无效）

1. **一任务一分支**：开工前 `git checkout -b feature/<使命名>`，禁止直接改 `main`。
2. **唯一写者**：`PROJECT.md`、`KNOWLEDGE.md`、`ROLES.md` **只有主会话（dsh）能写**，外部 agent 不得修改。改动信息通过 git 分支 + 达成报告传递。
3. **pre-commit hook 约束**：项目已装 git pre-commit hook，自动拦截对 `PROJECT.md` / `KNOWLEDGE.md` 的直接提交。主会话提交共享文档时需先 `touch .main-writer-flag`（提交后自动删除），外部 agent **不应使用此标记**。
4. **先看后改**：改任何文件前，先看 `.dsh\missions\` 有没有别的使命在碰同一文件；有冲突 → 停下，等用户裁决，不抢写。
5. **小步提交**：一个功能/修复一次 commit，message 用英文：`feat(Z<项目字母><序号>): ...` / `fix(...): ...` / `refactor(...): ...`（如 `feat(ZA02): ...`）。
6. **不扩大范围**：只改任务要求的文件；中途要扩大改动范围 → 先通知用户，不许悄悄改别的。
7. **开工前同步 main**：任务开始前 `git fetch {体系根}/<项目> main`（把 dsh 主工作区当远程源路径 fetch），确保基于最新代码干活，减少合并冲突。

## 五、zcode 内部三级会话（zcode 侧组织方式）

zcode 内部也采用主/副/域会话模式，与 dsh 侧平行。**每个项目在 zcode 侧有自己独立的一套 zcode 主/域会话**，各管本项目、用本项目号段：

| zcode 角色 | 怎么开 | 职责 |
|---|---|---|
| 主会话 | zcode 主窗口（对话1） | 统筹：读本项目 `PROJECT.md` 登记表取下一个 `Z<项目字母>##` 号 → 拆任务 → 派发到域会话 → **读域会话的达成报告并验收** → 合并/通知 dsh 主会话 |
| 域会话 | zcode 新开对话（对话2、3…） | 执行：使命名 `Z<项目字母>##-xxx`，在 zcode worktree 开 `feature/Z<项目字母>##-xxx` 分支，小步提交 `feat(Z<项目字母>##):`，**完成后自己写达成报告到 `.dsh\missions\<使命名>.md`（5 段格式，见第七节）** |
| 副会话 | zcode 内置 **Explore 子智能体**（只读） | 答疑：调用链梳理、代码调研、纯问答，不改文件 |

**报告由域会话写**（有第一手信息：改了哪些文件/哪里可能崩/怎么测的），主会话只读+验收，不代写。这跟 dsh 侧域会话写报告对齐。

> **两种派发来源（2026-08-30 明确）**：zcode 域会话可能由 zcode 主会话派发，也可能由 dsh 主会话直接派发（用户复制任务卡）。**无论谁派发，报告规则不变**：域会话干完自己写 `.dsh\missions\<使命名>.md`（5 段），两端主会话都能读该文件。

## 六、工作流（每个任务固定循环）

```
1. 读 PROJECT.md + KNOWLEDGE.md（了解项目）+ 看 .dsh\missions\（查冲突）
2. git fetch {体系根}/<项目> main（同步最新代码）
3. git checkout -b feature/<使命名>
4. 改代码（小步 commit，message 带 Z<项目字母>## 编号）
5. 写达成报告：.dsh\missions\<使命名>.md（5 段格式，见下方模板）——由域会话自己写
6. 结束（不合并，不写 PROJECT.md——主会话统一做）
```

---

## 七、达成报告模板（`.dsh\missions\<使命名>.md`）

> **唯一源＝`templates\dispatch-template.md` 的「达成报告」节**（2026-10-18 定）。本节**保留可复制的骨架**（外部 agent 读不到别的文件），但**字段含义以 dispatch 那节为准**；两边不一致时，以 dispatch 为准并回头改本节。

> 由**域会话自己写**（无论谁派发）。必填 5 段与 dsh 域会话对齐：[文件清单][依赖新增][未处理异常][接口签名][自测用例]。
> 前 4 字段必填，缺任一 = 报告不完整，主会话退回补齐；[接口签名] 仅接口变更类任务必填，非接口任务写 N/A。
> 参考示例：`{体系根}\项目甲\.dsh\missions\Z01-add-daily-articles-layer.md`（旧制编号，实际跑过的完整报告；新任务文件名用 `Z<项目字母>##-xxx.md`）。

```markdown
# 使命达成报告：<使命名>

- 分支：feature/<使命名>
- 完成时间：YYYY-MM-DD
- 改了什么：（一句话功能描述）

[文件清单]：仅列新增/修改的文件路径（相对项目根，一行一个）
[依赖新增]：引入第三方库写名称+版本号；未新增写"无"
[未处理异常]：哪里可能崩/什么场景会失败；无则写"无"
[接口签名]：涉及函数/API/数据结构签名变更才填（函数名+入参+出参）；不涉及写 N/A
[自测用例]：至少 1 个已实际执行并通过的手动测试（做了什么+预期+结果）

- 验收：（逐条对照任务要求，怎么验证的）
- 未完成/遗留：（没有则写"无"）
- 踩坑/注意：（给主会话合并时参考；没有则写"无"）
```

> 落盘位置说明：`.dsh\missions\` 在**项目文件夹内**（如 `{体系根}\项目甲\.dsh\missions\`，D 盘，不占 C 盘）。
> 两端主会话都通过 read 该文件获取报告——dsh 主会话直接读，zcode 主会话在应用内读。无需用户手动搬运报告文本。

## 八、冲突处理

- 改前看 `.dsh\missions\` 有活跃使命碰同一文件 → 停下，通知用户
- 用户裁决：合并使命 / 排队 / 拆分范围
- 不得各自为战

---

## 九、禁止事项清单

- ❌ 直接改 `main` 分支
- ❌ 修改 `PROJECT.md` / `KNOWLEDGE.md` / `ROLES.md`（hook 会自动拦截提交）
- ❌ 使用 `.main-writer-flag`（主会话专用放行标记）
- ❌ 在 dsh 主工作区干活（只在自己的 worktree）
- ❌ 改任务范围外的文件（除非先通知用户）
- ❌ 提交不写 commit message 或写中文 message
- ❌ 删除 `.dsh\missions\` 里别人的达成报告
- ❌ 用别的项目的字母编号（字母是本项目专属，取自 1.2 表）

## 十、与 dsh 体系的分工

| 角色 | 工具 | 工作区 | 职责 |
|---|---|---|---|
| 主会话 | dsh | <项目> | 统筹规划 + 合并所有分支 + 唯一写者更新共享文档 |
| dsh 域会话 | dsh + `tools\mission.mjs` | <项目> | declare 使命 → 分支执行 → complete |
| 副会话 | dsh / 本地模型 | <项目> | 答疑解惑 |
| **zcode 主会话** | zcode | <项目>-zcode | 统筹 zcode 侧任务，写/验收达成报告 |
| **zcode 域会话** | zcode | <项目>-zcode | 开分支执行，提交带 `Z<项目字母>##` |
| **zcode 副会话** | zcode Explore 子智能体 | <项目>-zcode | 只读调研答疑 |

## 十一、接入步骤（给用户操作）

1. dsh 主会话派域会话建好 worktree（如 `{体系根}\项目甲-zcode\`）
2. 在 zcode 里打开 worktree 目录
3. 把本协议内容作为"系统提示/规则"喂给 zcode 主会话（或放项目根 `EXTERNAL-AGENT.md` 让工具自动读）
4. 派任务时，告诉它使命名（`Z<项目字母>##-xxx`，字母取本项目在 1.2 表的分配）和任务范围
5. 完成后检查它有没有违反铁律（尤其有没有碰 PROJECT.md、有没有在错误工作区干活）
